Commune — Full-Stack Deep Dive Real-time chat: 1:1 and group messaging, WebRTC audio/video, cursor-paginated history

Read this first This document describes the codebase as it actually is, not as it ought to be. It was written retrospectively, and nothing was fixed in the process. Where the implementation is weak or wrong, it says so and says so plainly. The point is an honest account of a real project, including its mistakes.

0. System Overview

Commune is a two-tier application: an Express backend over MongoDB (via Prisma) and a React + TypeScript single-page frontend. Users register, find each other, and exchange messages in 1:1 or group conversations. Conversations carry history that pages backwards on scroll, and any conversation can be escalated to an audio or video call over WebRTC.

The two-transport split — the defining architectural fact

Commune runs two independent realtime systems at once, split by feature:

ConcernTransportWhere
Message fan-outAbly (hosted pub/sub)chat.js publishes to channel chat-{chatId}
Call signalling, presence, typingSocket.IO (self-hosted)app.js, rooms user-{id} and {roomId}

Both are dependencies of both tiers — the frontend ships ably and socket.io-client; the backend ships both server SDKs.

Honest assessment There is no good reason for this. Socket.IO was already running, already had room semantics, and could have carried messages. Ably adds a paid vendor, a second reconnection path on the client, a second failure mode, and splits ordering guarantees across two systems that know nothing about each other. It reads as an incremental decision — Socket.IO for calls first, Ably reached for later when messaging needed fan-out — rather than a designed one.

Auth model

JWT bearer tokens on HTTP, verified per request by Auth.middleware.js. Every chat route sits behind it, and authorization (chat membership, group-admin rights) is checked inside the controllers rather than at the route layer.

The asymmetry that matters The HTTP layer is consistently guarded. The socket layer is not guarded at all — it accepts a client-supplied userId and joins that user's private room on request. So the same application enforces identity rigorously over REST and not at all over WebSocket. This is the single most important thing to understand about the security posture here.

1. Backend Bootstrap

src/app.js constructs the Express app, wraps it in an http.Server, and attaches Socket.IO to the same server so HTTP and WebSocket share a port.

CORS is configured twice, differently

const corsOrigins = type === "dev" ? devOrigins : prodOrigins;
app.use(cors({ origin: (origin, cb) => { /* allow-list check */ }, credentials: true }));

const io = new Server(httpServer, { cors: { origin: "*", credentials: true } });

Express gets a strict env-driven allow-list. Socket.IO gets "*". The allow-list is also built from six discrete env vars (DEV_URL1..3, PROD_URL1..3), so unset ones land in the array as undefined.

Middleware order

helmet → morgan → body parsers → express-session → Passport → a global rate limiter → routes → 404 → error handler.

Two things are worth noticing. The session secret is the literal string "commune", committed. And the rate limiter is global at 1000 requests per 15 minutes, so login and OTP verification share a budget with message fetching — which is to say they are not meaningfully rate limited at all.

2. Authentication

JWT + middleware

const decoded = jwt.verify(token, process.env.USER_ACCESS_SECRET);
user = await prisma.user.findUnique({ where: { id: decoded } });
if (!user) return res.status(401)...
req.user = user;

The token payload is the user id — signed as a bare string rather than a claims object. It works, but it means there is nowhere to put exp, iat, roles, or a token version, so revocation is impossible and expiry depends entirely on how the token was signed.

Every authenticated request costs a database round-trip to load the full user. That's a reasonable trade for correctness (a deleted user is rejected immediately), and it is the kind of thing you would cache later rather than design away now.

Google OAuth and OTP

Passport handles the Google strategy (controllers/auth/googleAuth.js, passport.js); express-session exists essentially to support that flow. A separate Otp model backs email verification and password reset, with codes emailed through EmailService. The Otp model has a createdAt but no expiry column and no TTL index — expiry is enforced in application code if at all.

3. Data Model

Prisma over MongoDB. Seven models: User, Chat, Message, MessageReadStatus, DeletedChat, InviteToken, Otp.

Relations

Membership is a MongoDB-style many-to-many with explicit id arrays on both sides — User.chatIds[] and Chat.userIds[]. Group admin is a separate single relation (Chat.adminId → User, named "GroupChats"), so a group has exactly one admin and it is a hard foreign key rather than a role table.

Chat also carries messagesIds[] alongside the Message.chatId back-reference — the relationship is materialised in both directions, which means both can drift.

Missing The schema declares no indexes at all. The hottest query in the product — messages for a chat, ordered by timestamp descending — has no supporting index.

The DeletedChat watermark — the best idea in the codebase

"Delete chat" in a two-party conversation is a genuinely awkward product problem: it must remove the conversation for you without destroying it for the other person, and it has to behave sensibly if the conversation later resumes.

Commune solves it with a per-user watermark rather than a flag or a soft-delete column:

model DeletedChat {
  userId    String
  chatId    String
  deletedAt DateTime
  @@unique([userId, chatId])
}

Deleting upserts deletedAt = now(). Reading filters messages to timestamp > deletedAt. The other party is untouched. If the conversation resumes, old messages stay hidden for the deleter while new ones appear normally — no resurrection of history they intended to clear.

Why this is the right shape A boolean isDeleted would have forced a choice between destroying shared history and leaving the chat visible. A per-message per-user tombstone would be correct but costs a row per message per user. The watermark gets the same semantics in one row per user per chat, and reading it is a single indexed lookup. This is the part of the project worth talking about in an interview.

4. Messaging Pipeline

Send path — POST /v1/chat/send

client │ POST /v1/chat/send { content, chatId, type, fileUrl } ▼ authMiddleware ── verify JWT, load user ▼ createMessage ├─ load chat + users ├─ 403 unless sender ∈ chat.users ← authorization, correctly enforced ├─ if fileUrl: append to content as text ← attachments not modelled ├─ prisma.message.create() ├─ ably.publish("chat-{chatId}", message) ← realtime BEFORE remaining writes ├─ prisma.chat.update({ lastModified }) └─ prisma.messageReadStatus.createMany({ ...sender, readAt: now }) ▼ 200 + message

Membership is checked properly. The ordering is the problem: the message is broadcast to subscribers before lastModified is updated and before the read-status row is written, and none of the four steps share a transaction. A crash between them leaves recipients holding a message the chat list doesn't know about.

Cursor pagination — GET /v1/chat/:chatId/messages

History pages backwards with a timestamp cursor, 20 at a time, using the fetch-one-extra trick to decide hasMore without a second count query:

take: limit + 1,
orderBy: { timestamp: "desc" }
...
const hasMore = messages.length > limit;
const messagesToReturn = hasMore ? messages.slice(0, limit) : messages;
return { messages: messagesToReturn, nextCursor: hasMore ? last.timestamp : null };

Choosing cursor over offset pagination is correct and deliberate: offset pagination in a live message list skips or repeats rows whenever a message arrives mid-scroll. Two caveats — the cursor is a timestamp, which isn't unique under concurrent sends, and the where clause is assembled by two object spreads that both write the same timestamp key — currently correct only by accident of ordering.

The deleted-chat watermark composes into the same query, so a user who cleared a conversation pages through only what came after.

Unread counting

Read state is sparse: a MessageReadStatus row exists only once a user has read a message, and absence means unread. That's an efficient representation. The query built on top of it is not:

const unreadMessages = await prisma.message.findMany({ where: {...}, select: { id: true } });
res.json(unreadMessages.length);

Every unread row is fetched purely to be counted, with no upper bound. This should be count().

5. Realtime

Message delivery rides Ably channels named chat-{chatId}; the client subscribes per open conversation. Calls, typing indicators and per-user notification routing ride Socket.IO, with two room conventions:

RoomJoined byUsed for
user-{userId}register eventdirected events — incoming calls
{roomId}join eventconversation-scoped broadcast

Neither event is authenticated, and join performs no membership check. There is also no disconnect handler — Socket.IO leaves rooms automatically, but no application-level presence state is reconciled.

6. WebRTC Signalling

The server is a pure relay — it never touches media, only forwards SDP and ICE between peers. Four events: offer, answer, candidate, end-call. Each supports two addressing modes: to (a specific user, for 1:1) or roomId (everyone else in the conversation, for group calls).

A server B │ offer {to: B, from: A} │ │ ├──────────────────────────►│ emit → room user-B ─────────►│ │ │ │ answer {to: A} │◄───────────────── emit → room user-A ◄───────────────────┤ │ candidate (trickle ICE, both directions, relayed) │ │◄────────────────────────►│◄───────────────────────────►│ │ P2P media established │
Inconsistent trust candidate derives the sender from socket.data.userId — the server's own view. offer, answer and end-call take from straight from the client payload, along with callerName and callerAvatar. So identity is server-derived in one handler and client-asserted in three, in the same file. Caller identity is therefore spoofable.

7. Groups & Invites

Group operations are admin-gated in the controller: updateGroupChat and removeGroupMembers both compare chat.adminId to the caller and return 403 otherwise.

Joining works through InviteToken — a unique token row with an expiresAt, generated by generateInvite and consumed by acceptInviteLink, which checks expiry and whether the user is already a member before connecting them to the chat.

One product hole: deleteChat explicitly forbids the admin from deleting the group, and non-admins only disconnect themselves. So the only person with authority over a group is the only one who cannot remove it, and an abandoned group is permanent.

8. Sandbox System

An unusually product-minded piece of engineering for a portfolio project. Five fixed demo accounts (user1@gmail.com … user5@gmail.com) let a stranger try the full app — groups, calls, history — without signing up.

scripts/sandboxBackup.js → snapshot demo users + chats → sandbox_backup.json cron/sandboxReset.cron.js → nightly 00:00 IST jobs/resetSandbox.js → wipe demo-account data, restore from snapshot

Removing the signup barrier is exactly the right instinct for a project whose entire purpose is being clicked by a stranger who owes you nothing.

9. Frontend

React 18 + TypeScript + Vite, Tailwind, React Router 7. Server state is React Query; client state is Context.

LayerContents
api/A shared axios instance plus thin per-domain wrappers (auth, chat, message, user)
hooks/React Query hooks per domain — the only place components touch the network
context/CallContext (global call state, so a call survives navigation), ThemeContext
lib/socket.tsLazily-created Socket.IO singleton, autoConnect: false, websocket transport only

Hoisting call state into a context rather than the chat screen is the right call — an incoming call has to be answerable from anywhere in the app, which is why GlobalCallUI and IncomingCallPopup live above the router's content.

The component layer is flat: ~22 components in one directory, several of which (Chat, ChatArea, ChatBox, ChatSection, ChatBar, ChatRow) have names that don't disambiguate their roles.

10. What I'd Do Differently

Written as an engineer reviewing their own older work, in order of how much it would matter.

  1. Authenticate the socket handshake. One io.use() middleware verifying the same JWT the HTTP layer already verifies, with userId derived from the token and never from a payload. This single change closes the largest hole in the system, and the fact that HTTP got this right while WebSocket got no treatment at all is the clearest sign the two were built at different times with different care.
  2. Collapse to one realtime transport. Socket.IO was already there. Ably solves a problem that had already been solved in the same codebase, and the cost is a vendor, a second client runtime, and split ordering guarantees.
  3. Index the schema before writing the queries. A chat app whose primary query is "last N messages in this conversation" needs a compound index on (chatId, timestamp) before it needs anything else. Building cursor pagination carefully and then leaving the underlying query unindexed is optimising the wrong layer.
  4. Make the write path transactional, and publish after commit. Broadcasting before the durable writes complete inverts the correct order.
  5. Model attachments properly. Concatenating a file URL onto message text makes attachments unqueryable forever. The type column already existed to carry this.
  6. Prune the dependency list, and find out why socket-io is in it. A typosquat-shaped package name sitting next to the real one in a lockfile is worth understanding, not just deleting.
  7. Split chat.js. Nine hundred lines covering chats, messages, read state, groups, and invites is four modules wearing one filename.
Calibration The things this project got right are not accidental: the DeletedChat watermark is a genuinely good piece of modelling, cursor pagination was the correct choice over offset, HTTP authorization is enforced consistently, and the sandbox system shows product thinking most portfolio projects never reach. The failures cluster in one place — everything that arrived later and was bolted onto the side, which is the socket layer and the second realtime vendor. That is a useful pattern to recognise in one's own work.
